# infra

The backend's production is a single-node k3s cluster; every manifest lives here and **ArgoCD reconciles the cluster to `main`**. Nothing is applied by hand — changing production means committing to `infra/`, and a `kubectl` change is reverted by `selfHeal` within seconds. Rollback is `git revert` of the bump commit. How images get built and pinned is in `.github/CLAUDE.md`.

`infra/README.md` is the reference for the cluster: platform vs. application ArgoCD projects, SealedSecrets (and the master key that must be backed up outside the repo), the three Ingresses, the NetworkPolicy, and the MongoDB → R2 backup CronJob. Read it before touching anything here. `infra/` has three parts. `platform/` holds shared cluster add-ons, `apps/trellify/` holds the workload, and `clusters/<homelab|aws>/` holds only what differs per cluster. The ArgoCD entry point for each cluster is `clusters/<name>/argocd/kustomization.yaml`, so a new Application has to be listed there. Anything under `platform/` or `apps/trellify/overlays/prod` reaches **both** clusters. The README section "AWS Failover" covers the cold-standby EKS cluster: Terraform lives in `clusters/aws/terraform/`, the AWS cluster uses a separate Cloudflare tunnel, and `active_origin` in the Cloudflare stack is the only switch for API, ArgoCD and Grafana traffic; the client is served by Cloudflare whichever cluster is live, and a `git revert` of a bump does not roll it back (`wrangler rollback` does). `infra/README.md` stays descriptive: architecture and configuration only, no step-by-step procedures.

Changes under `infra/**` are checked by `.github/workflows/infra.yml` (`kustomize build` + `kubeconform -strict`, CRD schemas from the datreeio catalog, then a blocking `trivy config` scan at HIGH/CRITICAL). An accepted finding goes in `infra/.trivyignore.yaml` with a `statement` explaining why; every workload runs with `readOnlyRootFilesystem: true`, so a container that needs to write gets an `emptyDir` (usually `/tmp`). CI builds every folder with a `kustomization.yaml`, so a new manifest folder needs one or it goes unvalidated.

`apps/trellify/base/config-server.env` becomes a hash-suffixed ConfigMap through `configMapGenerator`; never convert it back to a plain ConfigMap manifest, or a config-only change stops rolling pods and silently never takes effect. A new server env variable goes there (or into SealedSecrets) as well as into the server's Zod schema.

## Dev cluster (kind + Tilt)

```bash
kind create cluster --config infra/clusters/dev/kind.yaml   # once; context kind-trellify
tilt up                                                     # http://localhost
tilt up -- --server-replicas=3                              # multi-pod, like prod; `tilt args` changes it live
```

The root `Tiltfile` installs ingress-nginx (same chart and platform values as ArgoCD, plus `infra/clusters/dev/ingress-nginx/values.yaml`), applies `infra/apps/trellify/overlays/dev`, and builds both images from the `dev` stage of each Dockerfile. In the server Dockerfile it sits **between** `builder` and the production stage so the default (last) target stays production; the client Dockerfile has only that stage, because production serves the client from Cloudflare. The client's Deployment, Service and `trellify-web` Ingress live in `overlays/dev/client.yaml`, not in `base`. `live_update` syncs `src/` and `packages/shared/src` into `tsx watch` / Vite. The overlay deletes what needs CRDs or R2 (ServiceMonitor, PrometheusRule, backup CronJobs) plus the HPA/PDB, and generates fixed dev Mongo/Redis secrets; `trellify-server-secrets` comes from the Tiltfile, which reads Brevo/Cloudinary/JWT from `apps/server/.env`. The server dev stage creates an empty `.env` because `src/config/environment.ts` throws when `NODE_ENV` is not production and the file is missing. The Tiltfile fails on any context other than `kind-trellify`.

## Cluster operations (Task)

`task` (go-task, run at the repo root from Git Bash, or from PowerShell with `C:\Program Files\Git\usr\bin` on `PATH`) lists the ops tasks for the clusters and prints the common flows (setup, failover, failback, load test). Task names are grouped by phase - `aws:setup:*`, `aws:dns:*`, `aws:failover:*`, `aws:failback:*`, `aws:status:*`, `aws:loadtest:*`, `homelab:setup:*`, `homelab:seal:*`, `homelab:deploy:*` - plus `client:*` for manual Workers deploy/rollback. The root `Taskfile.yaml` includes `infra/clusters/{aws,homelab}/Taskfile.yaml` and `aws/Taskfile.client.yaml`; `infra/clusters/Taskfile.data.yaml` (backup/restore/bloom-reset/restart) is included into both as the `data` namespace (`aws:data:*`, `homelab:data:*`) with its own `KUBECTL` var. Top-level `vars` of included Taskfiles are **global**, not per-file — a name defined in two of them silently resolves to one value everywhere, which is why the kubectl prefixes are `KC_AWS`/`KC_HOME`. Task ignores an `env:` entry whose variable is already set in the OS environment, so `PATH` cannot be extended from a Taskfile and an `AWS_PROFILE` already set in the shell would beat `env: AWS_PROFILE: trellify` - `AWS_PROFILE_GUARD` in the aws Taskfile refuses to run in that case; the root `UNIX_TOOLS` var fails every task early when `sed`/`grep`/`head` are missing, and heredoc tasks call `{{.BASH}}` (Git's `bash.exe` by full path) because a bare `bash` from PowerShell resolves to WSL's `System32\bash.exe`. Check any change with `task --dry <task>` before running it.

## Redis

`apps/trellify/base/redis/statefulset.yaml` overrides `command:`, which skips the image's `docker-entrypoint.sh` and its `--loadmodule` flags. `redis.conf` therefore carries an explicit `loadmodule /usr/local/lib/redis/modules/redisbloom.so`; delete that line and every bloom probe on the server fails open silently. The production Mongo StatefulSet does not set `GLIBC_TUNABLES`, so MongoDB's refusal to start on kernels 6.19+ applies to the homelab and EKS node kernels.
